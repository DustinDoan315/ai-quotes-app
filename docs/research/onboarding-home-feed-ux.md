# Onboarding, Home, and Feed UX: Source Note

**Research question:** What first-party platform guidance can inform an appealing Inkly flow from onboarding through photo capture/import, quote composition, saving, and browsing saved cards?

**Retrieved:** 2026-09-29.
**Scope:** Apple Human Interface Guidelines and developer documentation, Android Developers/Material guidance, and WCAG 2.2 for the directly relevant contrast threshold. The recommendations below are design guidance and synthesis, not conversion claims. Platform recommendations are labeled as such; WCAG thresholds apply when WCAG conformance is in scope.

## Practical direction for Inkly

Keep onboarding brief and skippable, then let the user make a quote with a real photo. Make **Take a photo** the clear creation action and offer **Choose a photo** as a separate route. Ask for camera access when the user starts capture; use the platform photo picker for import when selecting one or a few images is enough. After composition, show an editable preview, confirm the save, and place the saved quote where the user can find it in a clearly navigable feed. These are recommendations synthesized from the sources below, not claims that a particular flow guarantees higher conversion.

## Claim / evidence ledger

| UX claim and app implication | Evidence and status |
|---|---|
| **Teach the product through the first task.** If onboarding is useful, keep it brief and optional; let people try the core action rather than asking them to remember a slide deck. Put any tip beside the control it explains. | Apple HIG **recommends** onboarding be fast, fun, optional, and interactive; separate tutorials should be optional and skippable. If skipped, don’t present the tutorial again on later launches; keep it findable in Help, Account, or Settings. Put contextual tips near the relevant interface. For Inkly, demonstrate photo → quote → saved card, or make the first creation itself the tutorial. [Apple HIG: Onboarding](https://developer.apple.com/design/human-interface-guidelines/onboarding) |
| **Ask for camera access at the point of capture.** Explain the immediate purpose before showing the system prompt if the context alone is unclear; after denial, let the person continue into any feature that does not need the camera. If access is truly required, describe the feature impact neutrally and respect the choice; don’t use a Settings link or repeated prompts to persuade the user. | Apple HIG **recommends** requesting access only when a feature needs it, ideally when people use that feature, and avoiding launch-time prompts unless required. A custom pre-alert should have one button that clearly opens the system alert. Android **recommends** asking in context and gracefully degrading after denial; it explicitly says not to link to Settings to convince a user or persistently nag them. [Apple HIG: Privacy](https://developer.apple.com/design/human-interface-guidelines/privacy), [Android: Request runtime permissions](https://developer.android.com/training/permissions/requesting) |
| **Treat capture and import as different routes.** A user choosing an existing photo should not have to grant broad library access if a system picker satisfies the use case. | Apple documents that `PHPickerViewController` lets the user select assets without authorizing the app for the full Photos library. Android’s Photo Picker grants access to selected media rather than the entire library. Prefer those pickers for a single-photo quote flow; request broader library access only if a real product feature needs direct library browsing or PhotoKit/MediaStore operations. [Apple: Photos picker privacy experience](https://developer.apple.com/documentation/photokit/delivering-an-enhanced-privacy-experience-in-your-photos-app), [Android: Photo picker](https://developer.android.com/training/data-storage/shared/photo-picker) |
| **App-specific permission threshold: don’t gate Home’s images-only import on broad library permission without verifying a platform need.** This repo pins Expo `~54.0.33` and `expo-image-picker` `~17.0.10`; `useHomeCamera.handleOpenGallery` requests media-library permission and returns on denial before calling `pickPhotoForQuote`, which invokes `launchImageLibraryAsync({ mediaTypes: "images" })`. | Expo SDK 54 describes `launchImageLibraryAsync` as displaying system UI and says `MEDIA_LIBRARY` is required on iOS 10 only. The page’s image-picker example comment says “No permissions request is necessary,” but the sample immediately calls `requestMediaLibraryPermissionsAsync()` anyway, so the example is internally inconsistent. Expo separately documents a permission need for a particular iOS **video** case; that exception does not match this images-only helper. Apple’s PHPicker and Android’s Photo Picker provide system-mediated selection without full-library access (Android grants access to selected media). **Assessment:** the Home preflight is likely unnecessary for this images-only flow and can block a first-time user before the picker opens if they deny it. **Recommendation:** confirm current behavior in fresh-build tests on the supported iOS and Android devices/OS versions before removing the preflight; the Expo sample inconsistency and platform implementation details make that check material. [Expo SDK 54: ImagePicker](https://docs.expo.dev/versions/v54.0.0/sdk/imagepicker/), [Apple: Photos picker privacy experience](https://developer.apple.com/documentation/photokit/delivering-an-enhanced-privacy-experience-in-your-photos-app), [Android: Photo picker](https://developer.android.com/training/data-storage/shared/photo-picker). Implementation reference: `package.json`, `src/features/home/useHomeCamera.ts`, and `src/utils/pickPhotoForQuote.ts`. |
| **Give Home a stable map and one obvious creation action.** Keep the primary sections easy to find; give the creation action the strongest visual emphasis, and place less frequent actions near the relevant content or in an overflow menu. | Apple HIG says tab bars represent top-level sections, preserve each section’s navigation state, should remain visible while navigating (except under a temporary modal), and benefit from labels; fewer tabs are generally easier to navigate. Android recommends a navigation bar for primary destinations (3–5 at one hierarchy level) and one highest-priority FAB action at a time, with secondary/rare actions elsewhere. These are platform **recommendations**, not a requirement to use tabs or a FAB. [Apple HIG: Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars), [Android: Layout and navigation patterns](https://developer.android.com/design/ui/mobile/guides/layout-and-content/layout-and-nav-patterns) |
| **Make each feed card one coherent quote, with a clear hierarchy.** Keep the quote/photo and its related metadata together; make opening the card and any save/share/edit controls understandable as separate actions. Avoid crowding every possible command into the card. | Android Material guidance describes cards as containment for related content/actions and advises grouping related content to guide people. Android’s layout guidance also says not to overwhelm a view with too many actions; its navigation guidance reserves one action for the highest priority and places additional/less frequent actions in secondary locations. Applying that to Inkly, one quote is a natural card subject; show the quote first and keep secondary actions visually subordinate. The card design specifics are **synthesis**, not prescribed Material card anatomy. [Android: Material components](https://developer.android.com/design/ui/mobile/guides/components/material-overview), [Android: Layout basics](https://developer.android.com/design/ui/mobile/guides/layout-and-content/layout-basics), [Android: Layout and navigation patterns](https://developer.android.com/design/ui/mobile/guides/layout-and-content/layout-and-nav-patterns) |
| **Do not make a gesture the only way to use a feature.** If a card can be swiped to reveal actions, provide a visible accessible action path too. Give icon-only controls meaningful spoken labels and expose state changes. | Android accessibility guidance says not to rely on gestures for all actions, to provide accessibility actions, and to label UI elements. Apple HIG says to provide alternative labels for key interface elements and describe meaningful images. Use labels such as “Open quote,” “Save quote,” and “Choose a photo,” and announce saved/selected state to assistive technology. [Android: Accessibility](https://developer.android.com/design/ui/mobile/guides/foundations/accessibility), [Apple HIG: VoiceOver](https://developer.apple.com/design/human-interface-guidelines/voiceover) |
| **Check actual hit areas, not just icon artwork.** | Apple’s button HIG says a button’s hit region should generally be at least **44 × 44 pt**. Android’s mobile accessibility guidance says touch targets should be at least **48 × 48 dp**, even if the visible control is smaller. These are platform **design recommendations** in platform-specific logical units; do not compare pt and dp as raw pixel values. Measure camera, gallery, save, share, navigation, and dismiss targets. [Apple HIG: Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons), [Android: Accessibility](https://developer.android.com/design/ui/mobile/guides/foundations/accessibility) |
| **Verify contrast from rendered foreground/background pairs.** A text opacity such as “35% white” alone cannot establish a pass or failure: the rendered background, overlay, and text size affect the contrast ratio. | WCAG 2.2 Success Criterion 1.4.3 is a **Level AA conformance threshold**: at least **4.5:1** for ordinary text and **3:1** for large text, subject to its stated exceptions. Evaluate the actual composited card/photo backgrounds in normal presentation. Treat this as a benchmark when WCAG AA is a project requirement; it is not, by itself, a claim that every native app is legally required to conform to WCAG. [W3C: WCAG 2.2, SC 1.4.3](https://www.w3.org/TR/wcag/#contrast-minimum), [W3C: Understanding Contrast (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) |
| **Make transitions and outcomes legible.** After choosing an image, show which image is being used; after saving, clearly show that the quote was saved and where to view it. Preserve a way back to adjust or recover from mistakes where practical. | Apple’s design principles call for clear feedback about what is happening and easy recovery from mistakes. This supports the proposed confirmation/return path; the exact toast, animation, undo control, or persistence behavior is an Inkly design decision. [Apple HIG: Design principles](https://developer.apple.com/design/human-interface-guidelines/design-principles) |

## Thresholds and limits

- **44 × 44 pt (Apple)** and **48 × 48 dp (Android)** are platform guidance for touch targets, not a shared pixel threshold or legal conclusion.
- **4.5:1 / 3:1 (WCAG 2.2 AA)** are explicit contrast success-criterion thresholds when WCAG AA applies. Alpha/opacity percentages do not substitute for contrast measurement.
- For the current Home **images-only** import path, Expo SDK 54 documents a `MEDIA_LIBRARY` requirement only for iOS 10, while the repo requests it before launching the system picker. Treat the preflight as a likely avoidable first-use gate, but verify on supported devices before removing it; the Expo SDK example has contradictory comment/code.
- The cited platform documents do **not** set a universal onboarding screen count, feed-card aspect ratio, permission acceptance rate, or conversion benchmark. Avoid treating any such number as a source-backed threshold.
- Platform guidance is not evidence that a proposed design is attractive to Inkly’s audience. Validate the flow on-device and with users; measure completion and recovery behavior if product decisions depend on them.
